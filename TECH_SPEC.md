# IshMed — техническая шпаргалка для питча

**Дата:** 2026-08-16, после этапа двуязычия · Всё ниже **сверено с кодом и с живой базой**, а не с планами: `pytest --collect-only`, `wc -l`, `pg_proc`/`pg_policies`, журнал `ai.model_calls`.

**Два правила для сцены:**
1. Не говорить «у нас работает агент на LangGraph». Не работает — библиотека в зависимостях, схема `agent` под чекпоинты готова, кода графа нет. Интервью оказалось детерминированным автоматом, и это осознанный выбор (см. §4).
2. Не говорить «AI решает, кого нанять». AI спрашивает, расшифровывает и структурирует. Решение принимает человек, и промпт саммари запрещает вывод «подходит / не подходит» прямым текстом.

Ниже написано, что говорить вместо этого. Формулировки сильные и честные — извиняться не за что.

## 0. Главное за 30 секунд

Telegram-first платформа для клиник Узбекистана. Три поверхности, один Postgres, один Python-бэкенд:

| Поверхность | Кто пользуется | Технология | Статус |
|---|---|---|---|
| `@ishmedsifatbot` | пациенты по QR | aiogram 3.30 + Azure STT | **работает end-to-end**, RU/UZ |
| Веб-кабинет `app.ishmed.ezgupro.uz` | клиника | FastAPI + React 19 | **работает**: структура, штат, отзывы, QR, вакансии с авто-интервью. RU/UZ |
| `@ishmedbot` | медики | aiogram + Azure (5 деплойментов) | **работает end-to-end**: витрина вакансий, отклик, интервью голосом. RU/UZ |

Все три поверхности двуязычны: русский и узбекский. Язык — свойство человека, лежит в `product.users.locale` и один для бота и кабинета.

Главный технический тезис, произнести дословно:

> **Гарантии приватности мы вынесли в базу данных, а не в код приложения.** Причина прямая: решение о том, какие данные запросить, в перспективе принимает LLM. Код можно уговорить промптом. `REVOKE` уговорить нельзя.

Это же и ответ на вопрос «почему у вас так много SQL и так мало агента» — порядок работ выбран сознательно.

## 1. Архитектура

```
пациент ──QR──▶ t.me/ishmedsifatbot ──┐
                                       │  aiogram, long polling
медик ─────────▶ t.me/ishmedbot ───────┤
                                       ▼
клиника ──▶ nginx ──▶ uvicorn ──▶  Python (app/services/*)  ──▶ PostgreSQL 18.6
             (TLS)    FastAPI            │                       + pgvector 0.8.6
             React 19 SPA                └──▶ Azure OpenAI          RLS на 27 таблицах
                                              gpt-5 · gpt-5-mini    35 SECURITY DEFINER
                                              transcribe · tts      функций-дверей
```

Одна Azure VM (`Standard_B2as_v2`, 2 vCPU / 7.8 GB, Ubuntu 24.04, swedencentral). Всё нативно, **докера нет намеренно**: на двух ядрах он забирает ресурс и не даёт выигрыша на одной машине. Три unit-файла systemd с `Restart=always` и песочницей (`ProtectSystem=strict`, `NoNewPrivileges`, `ProtectHome`, `PrivateTmp`).

PostgreSQL слушает только `127.0.0.1`, порт 5432 закрыт на NSG. С ноутбука — через SSH-туннель. TLS: один сертификат Let's Encrypt на 4 имени, **certbot в режиме `certonly --webroot`**, конфигом nginx владеет репозиторий. Причина: `certbot --nginx` дописывает свои блоки в тот же файл, и очередной деплой затирал их вместе с прослушиванием 443. Один хозяин на один файл.

**Почему long polling, а не webhook.** Зона DNS рассинхронизирована между авторитативными NS, часть резолверов её не видит. Завязывать доставку апдейтов на резолвинг домена нельзя. Polling работает одинаково с ноутбука и с сервера, входящий порт не нужен. — `app/bot/main.py:3-8`

## 3. Где AI. Честная разбивка на три уровня

Самый вероятный вопрос от жюри. Отвечать по уровням, не смешивая их.

### Уровень 1 — работает в проде, вызывается живьём

Пять деплойментов Azure OpenAI (swedencentral), и все пять реально вызываются. Числа ниже — из журнала `ai.model_calls`, куда пишется каждый вызов с задержкой и токенами:

| Деплоймент | Зачем | Замерено |
|---|---|---|
| `gpt-5` | разбор текста вакансии на поля, план вопросов, саммари интервью | 2.2 c разбор, 3.8 c саммари |
| `gpt-5-mini` | оценка ответа кандидата: «по делу или уточнить» | 1.2 c |
| `gpt-4o-transcribe` | расшифровка голосовых — и отзывов, и ответов на интервью | 1.2 c |
| `tts` | озвучка вопроса интервью | 0.9 c |
| `text-embedding-3-small` | сконфигурирован под базу знаний, кода пока нет | — |

Четыре инженерных решения, которые стоит назвать:

1. **Telegram отдаёт ogg/opus, и Azure принимает его напрямую** — проверено. Конвертация через ffmpeg не нужна: минус процесс, минус зависимость, минус секунда задержки. `tts` тоже отдаёт ogg/opus, поэтому озвученный вопрос уходит в Telegram как голосовое без перекодирования. **Голос замкнут в обе стороны.**
2. **Блокирующий `urllib` уведён в `asyncio.to_thread`.** Иначе одна расшифровка застопорит весь polling, и остальные будут ждать чужое голосовое.
3. **`reasoning_effort=minimal` обязателен для диалога.** С рассуждением по умолчанию `gpt-5` отвечает 10.2 c против 2.3 c, и трёхминутное демо рассыпается.
4. **Оценка ответа ушла на `gpt-5-mini` осознанно.** Журнал показал 156 вызовов задачи «ответил человек по делу или нет» на старшей модели — там она не нужна. Это видно только потому, что есть журнал.

### Уровень 2 — контракт зафиксирован в базе, кода нет

**Векторный слой:** `product.kb_chunks` — `embedding vector(1536) NOT NULL`, индекс **HNSW** `vector_cosine_ops, m=16, ef_construction=64`. `ai.embedding_models` — реестр моделей с FK из `kb_chunks`, чтобы вектор нельзя было записать «неизвестно чем». `clinic_id` продублирован в чанки намеренно: RLS отсекает чужой тенант **до** векторного поиска, без джойна. — `014:180-199`, `006:8-20`

Формулировка для сцены: «Векторный слой не прикручивается в последний день. Схема, размерность, индекс, реестр моделей и изоляция тенанта уже в базе и покрыты правами.»

### Уровень 3 — квоты и деньги, посчитанные, а не оценённые

Замерено `az cognitiveservices`, не взято из документации:

| Деплоймент | Запросов/мин | Квота подписки |
|---|---|---|
| `gpt-5` | 2000 | 200 из 1000 |
| `gpt-5-mini` | 200 | 200 из 1000 |
| `gpt-4o-transcribe` | 10 000 | 100 из 400 |
| `tts` | **3** | **3 из 3, потолок** |

**`tts` — единственное узкое место, и оно жёсткое:** поднять квоту нельзя. Отсюда инженерное следствие: вопросы плана фиксированы, запись у них одна для всех кандидатов, поэтому после первой отправки в `job_questions.voice_file_id` лежит Telegram `file_id`. **Один вызов `tts` на вопрос за всю жизнь вакансии вместо одного на кандидата** (миграция 032). Правка формулировки сбрасывает кэш триггером.

Стоимость по журналу: **интервью целиком $0.0053 текстом, $0.0076 с голосовыми ответами.** На $5000 это порядка 660 000 интервью. Деньги — не ограничение, ограничение — квоты.

## 4. Авто-интервью: как база управляет моделью

Это лучший материал для питча. Не «мы дали LLM провести собеседование», а **«мы описали, что модели делать нельзя, и вынесли это туда, где она не сможет договориться»**.

**Работает целиком, живьём.** Цикл: клиника описывает вакансию словами → `gpt-5` разбирает текст на поля → менеджер проверяет → `gpt-5` предлагает 5–7 вопросов → **менеджер правит и одобряет** → публикация выдаёт deep link и QR → кандидат приходит по `t.me/ishmedbot?start=job_<код>` → отвечает текстом или голосом → клиника читает саммари, «о чём не сказал», «спросить лично» и полный транскрипт.

Прогон `make demo-interview` — три интервью подряд живым Azure. Проверено девять подряд без сбоев: интервью из шести вопросов занимает ~36 c машинного времени, между ответом и следующим вопросом ~4 c.

**Смысл публикации — не объявление, а собеседования, проведённые за клинику.** Клиника не выкладывает вакансию в чужой каталог, она получает разобранные ответы кандидатов.

### Пять правил, вынесенных из кода бота в базу

**1. Модель не выбирает, что спросить.** `next_interview_question()` выдаёт следующий вопрос из одобренного плана строго по `ord`, исключая уже заданные. Модель не может ни пропустить вопрос, ни переставить их, ни придумать свой.

> Обоснование в комментарии миграции: если модель придумывает вопросы на ходу, **двух кандидатов нельзя сравнить между собой** — они отвечали на разное. Сравнимость важнее гибкости диалога.

**2. Публикация невозможна без одобренного плана.** `interview_plan_status` — ENUM-подобный CHECK: `none → draft → approved`. `publish_job()` бросает `check_violation`, если план не `approved` **или в нём меньше трёх вопросов**. Иначе кандидат откликнется, начнёт интервью, а спрашивать будет нечего.

**3. Предел ходов считает база, а не только граф.** `interviews.turn_budget` (default 16, CHECK 4–40), `ask_interview_turn()` берёт строку `FOR UPDATE` и бросает `check_violation` при `asked_count >= turn_budget`. Комментарий: **диалог обязан заканчиваться, даже если кандидат отвечает не по делу.** Зацикленный агент — это счёт за токены и застрявший человек.

**4. Переиграть нельзя.** `interviews.application_id` — `UNIQUE`, а отклик уникален по `(job_id, candidate_id)`. Отсюда «одно интервью на вакансию для кандидата» **без отдельной проверки в коде**. Повторный `open_interview()` возвращает существующее интервью с его состоянием, а не начинает новое.

**5. Кандидат видит закрытый набор колонок.** `list_published_jobs()` и `get_published_job()` — `SECURITY DEFINER` с перечисленными полями. `source_text`, `extraction` и `created_by` наружу не выйдут, **даже если кто-то забудет отфильтровать их в коде**. Бот работает без контекста клиники: показывать надо вакансии всех клиник, поэтому RLS здесь не подходит, и дверь сделана функцией.

### Что ещё стоит упомянуть

- **`FORCE ROW LEVEL SECURITY`** — впервые в проекте, ровно на трёх таблицах интервью. RLS обходит владелец объектов; здесь этот обход закрыт.
- **Транскрипт строками, а не одним jsonb.** Клиника читает ход разговора: его удобнее отдавать постранично и связывать ответ с вопросом плана.
- **Аудио у себя не храним.** В `interview_turns` лежит `voice_file_id` Telegram и расшифровка в `answer_text`. Оригинал остаётся в Telegram.
- **Интервью не выносит решение о найме.** Дословно из комментария к таблице: «спрашивает, расшифровывает и структурирует, решает человек». Поля названы соответственно: `gaps` — «о чём кандидат не сказал: не минус кандидату, а подсказка клинике, что спросить»; `follow_ups` — «что стоит уточнить лично».
- **`job_questions.edited`** — флаг «менеджер правил формулировку модели». Полезно знать, насколько модели доверяют. Это метрика качества AI, встроенная в схему.
- **`origin` (`ai` / `manual`)** — видно, что предложила модель, а что дописал человек.
- **Публичный код вакансии** — 10 символов из алфавита без похожих глифов (`23456789abcdefghjkmnpqrstuvwxyz`): код диктуют голосом и набирают руками, «l» против «1» тут дороже лишнего символа. Уникальный индекс + CHECK на форму.

### Почему не LangGraph

Библиотека в зависимостях, схема `agent` под чекпоинты создана — и не используется. Причина честная и её стоит назвать самому: **интервью оказалось детерминированным конечным автоматом.** Состояние уже лежит в `product.interviews` и `interview_turns` — они знают, какой вопрос задан и на какой отвечено. Чекпоинтер добавил бы второй источник состояния и риск расхождения без единого выигрыша.

Практическое следствие, которое проверяется на демо: **бота можно перезапустить посреди разговора**, человек продолжит с того же места. Памяти в процессе нет вообще.

Граф станет оправдан, когда у интервью появятся ветвления — разные линии вопросов по ответам. Тогда база останется хранилищем, а чекпоинтер возьмёт на себя только позицию в графе.

### Что переводится, а что нет

Кандидат может быть узбекоязычным, а клиника — русскоязычной. Разложено так:

- **вопросы плана не переводятся.** Их написал и одобрил менеджер; подменять одобренное машинным переводом нельзя — кандидаты отвечали бы на разное, и сравнимость, ради которой всё построено, исчезла бы. Кандидат видит вопрос на языке клиники, а кнопки и подсказки на своём;
- **уточнение модель пишет на языке кандидата** — оно единственная реплика интервью, которую сочиняет она, а не менеджер;
- **саммари пишется на языке клиники.** `job_of_interview()` отдаёт `clinic_locale` — язык менеджера, создавшего вакансию (миграция 033). Решение принимает клиника, значит и читать ей.

## 5. Модель безопасности — три истории

### История 1. Контакты кандидата закрыты правами, а не проверкой в коде

```sql
REVOKE ALL ON product.candidate_contacts FROM ishmed_app;
-- «Это не упущение, а решение»   db/migrations/013:260-261
```

У прикладной роли **ни одного права** на таблицу с телефонами: ни SELECT, ни INSERT, ни UPDATE, ни DELETE. Почему все четыре, а не только SELECT: **запрет на чтение обходится через `UPDATE ... RETURNING`.** Половинчатый запрет — это отсутствие запрета.

Единственные двери — `SECURITY DEFINER` функции:

- `reveal_contact(invitation_id, actor_user_id)` — требует `status='accepted'`, проверяет, что запрашивающий является стороной сделки, **обязательно пишет `contact_revealed` в `consent_events`** и только потом читает контакт. `013:124-181`
- `save_contact(...)` — единственный путь записи. `013:184-210`
- `reveal_application_contact(...)` — то же для отклика, отдельной функцией: два разных пути к контакту должны читаться как два разных явления. `014:59-113`
- `forget_candidate(...)` — право на забвение: контакты и матчи удаляются, приглашения → `withdrawn`, профиль → `deleted` с обнулением transcript и extraction. `014:116-145`

Все с `SET search_path = pg_catalog, product`. Без этого функцию можно обмануть, подсунув свою схему раньше `product` — классическая атака на `SECURITY DEFINER`.

Тестов на один этот контур — **15**: пять вариантов SQL на невозможность доступа, пустой `information_schema.role_table_grants`, закрыт при `sent`, открыт после `accepted`, посторонний не видит даже после accept, `declined` не раскрывает, раскрытие попало в журнал.

### История 2. Изоляция тенантов: RLS на 27 таблицах

Контекст ставится через `set_config(..., is_local => true)` — живёт до конца транзакции и **не может протечь на следующий запрос из того же соединения пула**. Отдельный тест именно на это. — `app/db.py:53-85`

Ключевой принцип, произнести дословно: **не выставленный контекст означает «ничего не видно», а не «видно всё».** Забыли контекст — увидите пустоту, и это правильное поведение.

Два уровня политик:
- по тенанту — `ishmed.clinic_id`
- по роли внутри тенанта — `ishmed.member_role` → `product.is_manager()`, обёрнуто в `coalesce(..., false)`. **Неизвестная роль уменьшает права, а не расширяет.**

Двусторонние политики там, где данные принадлежат двум сторонам: `matches`, `invitations`, `applications`, `interviews`, `interview_turns` видны и клинике, и медику, но `WITH CHECK` на запись — только клинике.

`product.users`, `sessions`, `user_credentials` — **без RLS сознательно**: их читают до того, как контекст известен (медика ищут по `telegram_user_id`, сессию по хэшу токена). Политика, зависящая от контекста, сделала бы вход невозможным. Это решение с обоснованием в миграции, а не забытая таблица. — `013:42-47`

Отдельная тонкость, которую стоит рассказать: `product.user_clinic()` разрывает замкнутый круг на входе. `clinic_members` закрыта RLS по `clinic_id`, а на момент логина контекст тенанта ещё неизвестен — узнать его можно только из `clinic_members`. Функция отвечает ровно на один вопрос и ничего больше не отдаёт.

### История 3. Бизнес-правила как ограничения БД, а не как код

- **`ck_matches_reasons`**: `NOT hard_constraints_passed OR array_length(reasons,1) >= 2` — матч без двух объяснений **физически невозможно записать**. Требование объяснимости выражено ограничением, а не код-ревью.
- **`ck_credentials_hash_is_argon2`**: `password_hash LIKE '$argon2%'`. `accept_employee_invite()` бросает `check_violation`, если ей передали не-argon2: **пароль не проходит даже транзитом через аргумент функции.**
- **`staff_positions.seats_open`** — генерируемая колонка `GENERATED ALWAYS AS (seats - seats_filled) STORED`. «Вакантно / занято» не переключатель, а производная от факта: триггер `tr_employees_recount` пересчитывает при найме, увольнении и переводе — при переводе сразу обе позиции.
- **`ck_users_consent_pair`**: `(consent_at IS NULL) = (consent_version IS NULL)` — «полусогласия» не существует как состояния.
- **`ck_reviews_callback`**: просьба перезвонить без телефона не сохранится.
- **Rate limit внутри функции приёма:** веб — 1 отзыв на `(target, ip_hash)` в час, Telegram — **1 на цель в 24 часа**. Порог разный не случайно: аккаунт Telegram — устойчивая личность, сменить IP проще, чем аккаунт. Под каждый лимит свой индекс.
- **`is_correct` закрыт колоночным грантом:** `GRANT SELECT (id, question_id, clinic_id, position, text)`. Правильный ответ прикладная роль прочитать не может. Варианты перемешиваются `ORDER BY md5(option_id || attempt_id)`, чтобы «правильный всегда первый» не стало стратегией. Разбор попытки открывается только при `finished_at IS NOT NULL` — иначе это способ подсмотреть ответы.
- **Справочники пополняются миграцией, а не приложением** (`025`): по ним считается матчинг, и свободный ввод развалил бы сравнение кандидатов.

## 6. Отзывы по QR — рабочий цикл целиком

Это то, что показывается на демо живьём.

1. Менеджер в кабинете жмёт QR на подразделении или сотруднике → `ensure_*_review_target()` (идемпотентна, `clinic_id` выводит **из самого узла**, чужая клиника → `insufficient_privilege`).
2. `segno` рисует QR **на лету, без записи на диск**: файл пришлось бы инвалидировать и убирать за собой, а рисование занимает миллисекунды. SVG для печати (вектор + обязательный quiet zone), PNG для экрана.
3. Slug — 12 символов из алфавита **без похожих глифов**. Коротко ещё и потому, что deep link ограничен 64 символами `start`, а чем меньше данных в QR, тем крупнее модули и надёжнее считывание с расстояния.
4. Пациент наводит камеру → `t.me/ishmedsifatbot?start=<slug>` → оценка кнопками 1–5 → текст, голос или фото. Голос уходит в STT.
5. Пришёл в бота без QR — **не даём выбрать кабинет из списка.** Он не помнит, где был, а мы получим отзывы, привязанные наугад.
6. Резервная веб-форма `/r/{slug}` — серверный Jinja2 с инлайновым CSS, десяток килобайт. React туда не грузим: пациент открывает страницу на мобильном интернете в коридоре, и 280 КБ SPA ради одной формы — это не инженерия. Плюс honeypot-поле против простых ботов.
7. Отключение опроса вместо удаления цели: код напечатан и наклеен на стену, удалить цель значит превратить наклейку в битую ссылку без объяснения.
8. Кабинет показывает не средний балл, а **причину**: статистика по тегам «что просят улучшить», фильтры «низкие оценки», «не разобрано», «просят перезвонить», отметка «разобрано» с автором.

Здоровье, диагноз и лечение не спрашиваются **никогда** — список тегов закрытый (6 аспектов сервиса), и функция приёма отвергает тег вне справочника через `<@`. Тест на это подсовывает в тег SQL-инъекцию.

Файлы у себя не храним — только `file_id` Telegram. `ip_hash` вместо адреса, соль из ключа приложения, чтобы хэш нельзя было сверить с готовой радужной таблицей.

## 6-бис. Двуязычие: почему это инженерная задача, а не файл с переводами

Узбекистан двуязычен, и для медсестры из района русский текст — барьер, а не неудобство. Все три поверхности работают на русском и узбекском.

**Язык — свойство человека, а не поверхности.** Он лежит в `product.users.locale` (enum `ru`/`uz`) и один для бота и кабинета: медик выбрал узбекский на `/start` — менеджер той же клиники, если он тот же человек, получит узбекский кабинет.

| Поверхность | Откуда язык | Переключатель |
|---|---|---|
| `@ishmedbot` | `users.locale`, задан на `/start` | `/language` |
| `@ishmedsifatbot` | `language_code` из Telegram | кнопка под приветствием |
| Кабинет | `users.locale` через `/api/auth/me` | сегмент в панели → `POST /api/auth/locale` |

**Полнота держится механически, а не вниманием.** Это главное, что стоит сказать: дырка в переводе не ломает приложение — оно молча падает на русский, и узбекоязычный человек посреди узбекского диалога получает русскую фразу. Заметит зал, а не мы. Поэтому:

- на бэкенде `tests/test_i18n.py` сверяет паритет ключей **и совпадение подстановок** `{...}`: если в русском есть `{count}`, а в узбекском нет, тест падает;
- на фронте узбекская таблица объявлена как `Record<Key, string>` по русской — **забытый ключ не собирается**, это ошибка компиляции;
- пропущенный ключ в рантайме виден как `[ключ]`, а не как пустота.

**Грамматика, а не подстановка строк.** Русский требует трёх форм и разных падежей: «6 вопросов», но «опыт от 3 **лет**», а не «от 3 года». Отсюда `plural(n, prefix, locale)` и отдельные ключи для родительного падежа. В узбекском существительное после числительного не меняется — все три формы одинаковы, и правило остаётся одно на оба языка, а не ветвится по локали. Обе ошибки — «от 3 года» и оторванный суффикс «3 yil dan» вместо «3 yildan» — поймал тест, а не глаз.

**Что осознанно не переводится:** вопросы плана интервью и приветствие вакансии, написанное клиникой. Обоснование в §4.

Отзыв пациента сохраняет тот язык, на котором он реально оставлен, а не тот, что стоит в клиенте Telegram: человек мог переключить его кнопкой.

**Честно про качество:** узбекский написан без носителя языка. Полнота гарантирована, формулировки — нет. Это названный долг, а не умолчание.

**Про тесты сказать отдельно, это козырь:** они идут **против реальной PostgreSQL, а не против моков**. Дословно из `conftest.py`: половина того, что проверяется, — это права доступа, RLS и ограничения самой БД; на моках такие вещи не тестируются, там они всегда «работают».

Обвязка тестов — четыре решения, по которым видно уровень:

- **Два разных подключения принципиально.** Подготовка данных — под владельцем базы, сами проверки — под урезанной ролью `ishmed_app`, то есть ровно в тех условиях, в которых работают бот и веб.
- Тестовые пользователи получают **отрицательные `telegram_user_id`**: реальные Telegram ID всегда положительные, коллизия с живыми данными исключена.
- Уборка **перебором таблиц, а не `CASCADE`**: так сразу заметно, если появится таблица, о которой уборка не знает.
- Тест на вход сравнивает **время ответа** на неизвестный email и на неверный пароль, а не только текст сообщения.

## 8. Аутентификация клиники

argon2id, хэш в **отдельной таблице** — чтобы не попал в общий `SELECT` по пользователю и в сериализатор. В cookie случайный токен, в базе только его `sha256`. Тест проверяет, что токена нет в базе в открытом виде нигде.

Одинаковый ответ **и сравнимое время** на неизвестный email и на неверный пароль — иначе форма входа превращается в перебор существующих аккаунтов. Блокировка на 15 минут после 8 попыток, счётчик **в БД, а не в памяти процесса** (иначе перезапуск сбрасывает защиту), `Retry-After` в ответе. Просроченные сессии чистятся на старте сервиса: он перезапускается при каждом деплое, отдельное расписание не нужно.

Два рубежа на управленческих разделах: RLS в базе **и** 403 на уровне HTTP. Не дублирование — RLS уже не отдаст чужие данные, но внятный 403 лучше пустого списка: иначе непонятно, сломалось или не положено.

Отдельная история про найденный и закрытый баг: приглашение сотрудника в портал изначально выдавало роль `recruiter` вместо `employee`, то есть рядовой сотрудник получал менеджерские права. Починено миграцией 022 вместе с `UPDATE` уже созданных аккаунтов, и на это написан регрессионный тест — плюс проверка, что сотрудник видит 0 строк в семи управленческих таблицах.

## 9. Что спросят — и что отвечать

**«Где здесь AI, кроме распознавания речи?»**
Четыре живых деплоймента на разных задачах: `gpt-5` разбирает свободный текст вакансии на поля и собирает саммари интервью, `gpt-5-mini` решает, достаточен ли ответ кандидата, `gpt-4o-transcribe` расшифровывает голос, `tts` озвучивает вопросы. Каждый вызов пишется в `ai.model_calls` с задержкой и токенами — отсюда и стоимость интервью посчитана, а не оценена: $0.0053 текстом, $0.0076 с голосом.

**«А агент-то где? LangGraph у вас в зависимостях.»**
> Мы его написали и выбросили — точнее, не стали писать, когда стало видно, что задача другая. Интервью оказалось детерминированным автоматом: порядок вопросов фиксирован планом, состояние уже лежит в двух таблицах. Чекпоинтер дал бы второй источник правды и риск расхождения без выигрыша. Граф станет оправдан на ветвлениях — разных линиях вопросов по ответам; тогда база останется хранилищем, а чекпоинтер возьмёт позицию в графе. Схема `agent` с правом записи ровно на неё уже стоит. Это не «не осилили», а «не понадобилось, и мы можем объяснить, когда понадобится».

**«Почему не векторный поиск для матчинга?»**
Пробовали и отказались по данным. В исходном каталоге 1 305 врачебных названий против 54 медсестринских — соотношение 24:1. Семантический поиск на таком распределении стабильно ставит врача выше медсестры на вакансию медсестры. Для медицинского найма это не «неточность», а недопустимый результат: категория роли — hard constraint, не предпочтение. Поэтому матчинг детерминированный, а `ck_matches_reasons` требует минимум две причины у каждого матча.

**«Почему не Docker / Kubernetes?»**
Одна VM, два ядра. Докер там забирает ресурс и не даёт выигрыша. systemd с `Restart=always` и песочницей закрывает ту же задачу. Появится вторая машина — разговор изменится.

**«Как проверите, что приватность действительно работает?»**
`make verify`: ruff + проверка секретов + 154 теста против живой базы под прикладной ролью. Тест «нет доступа к контактам» — регрессионный барьер: если он упал, это не тест сломался.

**«Вы никого не парсите?»**
Больше нет. Миграция 023 снесла импортированный каталог — 3 595 вакансий и 773 организации с госпортала, вместе с эмбеддингами и гибридным поиском. В базе живут только вакансии, которые клиника опубликовала сама. База после чистки 12 MB вместо 93.

**Как** снесли — рассказать отдельно, это показывает уровень. Не `DROP SCHEMA CASCADE`: одиннадцать триггеров `updated_at` в схеме `product` вызывали функцию из удаляемой схемы, и каскад снёс бы их молча — поле просто перестало бы обновляться по всему продукту. Функцию перенесли, триггеры перевесили **перебором по `pg_trigger`**, а не по списку, чтобы забытый триггер не обнаружился тем, что данные тихо перестали обновляться.

**«Что сломается на демо?»**
Telegram polling — single-consumer: поднят серверный бот — локальный откажется стартовать, и наоборот. Сеть до Azure — единственная внешняя зависимость. Незаполненные разделы кабинета показывают честные пустые состояния, а не выдуманные карточки: на репетиции фальшивые данные легко принять за настоящие, и это худший способ узнать, что раздел не работает.

## 10. Долги — знать, чтобы не подловили

Если жюри найдёт это раньше вас, будет хуже. Лучше назвать самому.

**Дыры в правах — исправить до демо, если будет время:**

1. **`product.course_answer_key()` не проверяет роль менеджера.** В комментарии сказано «только владельцем клиники», в теле — только совпадение `clinic_id`. Сотрудник с выставленным контекстом получает ключ ответов и обходит весь контур с колоночным грантом на `is_correct`. Закрывается одной строкой `is_manager()`.
2. **`p_candidates_own` не переписана под роль.** Миграция 022 перечисляет `candidate_profiles` как управленческую таблицу, но политику не изменила: сотрудник с ролью `employee` увидит все активные профили кандидатов. Тесты не ловят — таблицы нет в списке `MANAGEMENT_TABLES`.
3. **`attach_to_review()` не проверяет право на конкретный отзыв.** Зная `review_id`, можно приложить вложение к любому. Защита сейчас в том, что `review_id` только что вернула `submit_review_telegram`.

**Незакрытый объём:**

4. **Схема курсов есть, API и UI — нет.** Шесть таблиц, оценивание, перемешивание, колоночный грант — всё в миграции 021. Раздел «Обучение» в кабинете — заглушка.
5. **Матчинг и приглашения не написаны.** Таблицы `matches`, `invitations` и `ck_matches_reasons` есть, чистой функции ранжирования нет. Раздел «Кандидаты» — заглушка.
6. **Профиль кандидата не дополняется из интервью.** `extraction` собирается и лежит в `interviews`, но `candidate_profiles` остаётся черновиком.
7. **Имя кандидата в кабинете не показывается** — только «Кандидат <8 символов id>». Это намеренно (контакт закрыт до принятия отклика), но менеджеру неудобно, и решения пока нет.
8. **Напоминания о брошенном интервью нет.** `status='in_progress'` и старый `last_activity_at` никто не разбирает.

**Процесс и инфраструктура:**

9. **`test_rls_is_enabled_on_all_tenant_tables` проверяет 10 таблиц из 27.** Докстринг называет его «страховкой от новой таблицы, которую забыли закрыть политикой» — страховка отстала от схемы.
10. **Мёртвые гранты** на снесённые `core.*` и `ai.search_vacancies` остались в 011. Миграции иммутабельны, чистить только новым файлом.
11. **CI нет**, `make verify` прогоняется руками: тесты требуют живой БД через SSH-туннель.
12. **Узбекский написан без носителя языка** — и в ботах (`app/i18n/uz.py`), и в кабинете (`frontend/src/lib/i18n.tsx`). Полнота ключей держится тестом и типами, но качество формулировок не проверено, особенно текст согласия. Это единственный долг по локализации: сама двуязычность работает на всех трёх поверхностях.
13. **Промпты слушаются не полностью.** Модель добавляет в требования то, чего в тексте не было, и склеивает два вопроса в один через «и», хотя промпт это запрещает. Поэтому оба шага проходят через правку менеджером, а не сохраняются молча.
14. **Токен бота утёк в переписку** — нужен `/revoke` у @BotFather до публичного демо.
15. Ночные дампы лежат на том же диске, что база. Azure Backup для VM не включён.

> **Privacy guarantees live in the database, not in application code.** The reason is direct: an LLM will eventually be the thing deciding which data to request. You can talk code into anything with a prompt. You cannot talk `REVOKE` into anything.

That is also the answer to "why so much SQL and so little agent" — the ordering was chosen deliberately.

## 1. Architecture

```
patient ──QR──▶ t.me/ishmedsifatbot ──┐
                                       │  aiogram, long polling
medic ─────────▶ t.me/ishmedbot ───────┤
                                       ▼
clinic ──▶ nginx ──▶ uvicorn ──▶  Python (app/services/*)  ──▶ PostgreSQL 18.6
            (TLS)    FastAPI            │                       + pgvector 0.8.6
            React 19 SPA                └──▶ Azure OpenAI          RLS on 27 tables
                                             gpt-5 · gpt-5-mini    35 SECURITY DEFINER
                                             transcribe · tts      gatekeeper functions
```

A single Azure VM (`Standard_B2as_v2`, 2 vCPU / 7.8 GB, Ubuntu 24.04, swedencentral). Everything runs natively; **no Docker, on purpose**: on two cores it consumes resources without paying for itself on one host. Three systemd units with `Restart=always` and sandboxing (`ProtectSystem=strict`, `NoNewPrivileges`, `ProtectHome`, `PrivateTmp`).

PostgreSQL listens on `127.0.0.1` only, and port 5432 is closed at the NSG. Laptop access goes through an SSH tunnel. TLS: one Let's Encrypt certificate covering 4 names, with **certbot in `certonly --webroot` mode** and the nginx config owned by the repository. The reason: `certbot --nginx` appends its own blocks to the same file, and a subsequent deploy once wiped them along with the 443 listener. One owner per file.

**Why long polling instead of webhooks.** The DNS zone is out of sync between authoritative nameservers, so a share of resolvers cannot see it. Tying update delivery to domain resolution is not acceptable. Polling behaves identically from a laptop and from the server, and needs no inbound port. — `app/bot/main.py:3-8`

## 3. Where the AI is. Three honest tiers

The most likely question from the judges. Answer tier by tier, without blurring them.

### Tier 1 — in production, invoked for real

Five Azure OpenAI deployments (swedencentral), and all five are actually called. The numbers below come from the `ai.model_calls` journal, where every call is logged with its latency and token usage:

| Deployment | What for | Measured |
|---|---|---|
| `gpt-5` | parsing vacancy free text into fields, question plan, interview summary | 2.2 s parse, 3.8 s summary |
| `gpt-5-mini` | judging a candidate's answer: "on point, or ask again" | 1.2 s |
| `gpt-4o-transcribe` | transcription of voice — both reviews and interview answers | 1.2 s |
| `tts` | reading interview questions aloud | 0.9 s |
| `text-embedding-3-small` | configured for the knowledge base; no code yet | — |

Four engineering decisions worth naming:

1. **Telegram serves ogg/opus and Azure accepts it directly** — verified. No ffmpeg conversion: one fewer process, one fewer dependency, one second less latency. `tts` also returns ogg/opus, so a spoken question goes to Telegram as a voice message with no re-encoding. **Voice is closed in both directions.**
2. **The blocking `urllib` call is moved into `asyncio.to_thread`.** Otherwise a single transcription stalls the whole polling loop and everyone else waits on someone's voice note.
3. **`reasoning_effort=minimal` is mandatory for dialogue.** With default reasoning `gpt-5` answers in 10.2 s versus 2.3 s, and a three-minute demo falls apart.
4. **Answer judging was moved to `gpt-5-mini` deliberately.** The journal showed 156 calls of "did the person answer to the point" landing on the larger model, where it buys nothing. That is only visible because the journal exists.

### Tier 2 — the contract is fixed in the database, the code is not written

**Vector layer:** `product.kb_chunks` — `embedding vector(1536) NOT NULL`, an **HNSW** index `vector_cosine_ops, m=16, ef_construction=64`. `ai.embedding_models` is a model registry with an FK from `kb_chunks`, so a vector cannot be written by an unknown model. `clinic_id` is deliberately denormalised into chunks so RLS cuts off other tenants **before** the vector search, with no join. — `014:180-199`, `006:8-20`

Phrasing for the stage: "A vector layer is not something you bolt on the last day. Schema, dimensionality, index, model registry and tenant isolation are already in the database and covered by grants."

### Tier 3 — quotas and money, counted rather than estimated

Measured with `az cognitiveservices`, not taken from the docs:

| Deployment | Requests/min | Subscription quota |
|---|---|---|
| `gpt-5` | 2000 | 200 of 1000 |
| `gpt-5-mini` | 200 | 200 of 1000 |
| `gpt-4o-transcribe` | 10,000 | 100 of 400 |
| `tts` | **3** | **3 of 3, hard ceiling** |

**`tts` is the only bottleneck, and it is a hard one:** the quota cannot be raised. Hence the engineering consequence: plan questions are fixed and their recording is identical for every candidate, so after the first send `job_questions.voice_file_id` holds a Telegram `file_id`. **One `tts` call per question for the entire life of the vacancy, instead of one per candidate** (migration 032). Editing the wording drops the cache via a trigger.

Cost from the journal: **an entire interview costs $0.0053 in text, $0.0076 with voice answers.** On $5,000 that is roughly 660,000 interviews. Money is not the constraint; quotas are.

## 4. Auto-interview: how the database governs the model

This is the best pitch material. Not "we let an LLM run an interview," but **"we specified what the model is not allowed to do, and put those rules where it cannot negotiate."**

**It works end-to-end, live.** The loop: a clinic describes a vacancy in plain words → `gpt-5` parses the text into fields → the manager checks them → `gpt-5` proposes 5–7 questions → **the manager edits and approves** → publishing yields a deep link and a QR code → the candidate arrives via `t.me/ishmedbot?start=job_<code>` → answers in text or by voice → the clinic reads the summary, the "did not mention" list, the "ask in person" list and the full transcript.

`make demo-interview` runs three interviews back to back against live Azure. Nine consecutive runs verified without a failure: a six-question interview takes ~36 s of machine time, with ~4 s between an answer and the next question.

**The point of publishing is not an advert, it is interviews conducted on the clinic's behalf.** A clinic does not post a vacancy into someone else's catalogue; it receives structured candidate answers.

### Five rules moved out of bot code and into the database

**1. The model does not choose what to ask.** `next_interview_question()` returns the next question from the approved plan strictly by `ord`, excluding ones already asked. The model cannot skip a question, reorder them, or invent its own.

> The rationale in the migration comment: if the model invents questions on the fly, **two candidates cannot be compared** — they answered different things. Comparability outranks conversational flexibility.

**2. Publishing without an approved plan is impossible.** `interview_plan_status` is a CHECK-constrained `none → draft → approved`. `publish_job()` raises `check_violation` if the plan is not `approved` **or holds fewer than three questions**. Otherwise a candidate applies, starts an interview, and there is nothing to ask.

**3. The turn limit is enforced by the database, not only by the graph.** `interviews.turn_budget` (default 16, CHECK 4–40); `ask_interview_turn()` takes the row `FOR UPDATE` and raises `check_violation` once `asked_count >= turn_budget`. The comment: **a dialogue must end, even if the candidate answers off-topic.** A looping agent is a token bill plus a stuck human.

**4. No replays.** `interviews.application_id` is `UNIQUE`, and an application is unique per `(job_id, candidate_id)`. That yields "one interview per vacancy per candidate" **with no separate check in code**. Calling `open_interview()` again returns the existing interview and its state rather than starting a new one.

**5. The candidate sees a closed column set.** `list_published_jobs()` and `get_published_job()` are `SECURITY DEFINER` with explicitly enumerated fields. `source_text`, `extraction` and `created_by` cannot leak **even if someone forgets to filter them in code**. The bot runs without a clinic context because it must show vacancies from every clinic, so RLS does not fit here and the door is a function instead.

### Also worth mentioning

- **`FORCE ROW LEVEL SECURITY`** appears for the first time in the project, on exactly the three interview tables. RLS is normally bypassed by the object owner; here that bypass is closed.
- **The transcript is rows, not one jsonb blob.** The clinic reads the conversation, so it is easier to paginate and to link each answer back to its planned question.
- **We never store audio.** `interview_turns` holds the Telegram `voice_file_id` plus the transcript in `answer_text`. The original stays in Telegram.
- **The interview does not make hiring decisions.** Verbatim from the table comment: it asks, transcribes and structures; a human decides. The fields are named accordingly: `gaps` is "what the candidate did not mention — not a mark against them, but a hint to the clinic about what to ask"; `follow_ups` is "what is worth clarifying in person."
- **`job_questions.edited`** flags "a manager rewrote the model's wording." Useful for knowing how much the model is trusted — an AI quality metric built into the schema.
- **`origin` (`ai` / `manual`)** makes it visible what the model proposed versus what a human added.
- **The public vacancy code** is 10 characters from a confusable-free alphabet (`23456789abcdefghjkmnpqrstuvwxyz`): the code gets dictated aloud and typed by hand, so "l" versus "1" costs more than an extra character. Unique index plus a CHECK on shape.

### Why not LangGraph

The library is in the dependencies and the `agent` checkpoint schema exists — unused. The honest reason is worth volunteering: **the interview turned out to be a deterministic state machine.** Its state already lives in `product.interviews` and `interview_turns`, which know which question was asked and which was answered. A checkpointer would add a second source of state and a risk of divergence, for no gain.

The practical consequence, demonstrable on stage: **the bot can be restarted mid-conversation** and the person continues from the same place. There is no in-process memory at all.

A graph becomes justified once interviews branch — different question lines depending on answers. At that point the database stays the store and the checkpointer only owns the position in the graph.

### What gets translated and what does not

A candidate may be Uzbek-speaking while the clinic is Russian-speaking. The split:

- **plan questions are not translated.** A manager wrote and approved them; substituting machine translation for approved wording would mean candidates answer different things, destroying the comparability the whole design exists for. The candidate sees the question in the clinic's language and the buttons and hints in their own;
- **the follow-up is written in the candidate's language** — it is the only line of the interview the model composes rather than the manager;
- **the summary is written in the clinic's language.** `job_of_interview()` returns `clinic_locale`, the language of the manager who created the vacancy (migration 033). The clinic makes the decision, so the clinic gets to read it.

## 5. The security model — three stories

### Story 1. Candidate contacts are closed by grants, not by a check in code

```sql
REVOKE ALL ON product.candidate_contacts FROM ishmed_app;
-- "This is a decision, not an oversight."   db/migrations/013:260-261
```

The application role holds **no privileges at all** on the table containing phone numbers: no SELECT, no INSERT, no UPDATE, no DELETE. Why all four rather than SELECT alone: **a read ban is trivially bypassed via `UPDATE ... RETURNING`.** A partial ban is no ban.

The only doors are `SECURITY DEFINER` functions:

- `reveal_contact(invitation_id, actor_user_id)` — requires `status='accepted'`, verifies the caller is a party to the deal, **mandatorily writes a `contact_revealed` row into `consent_events`**, and only then reads the contact. `013:124-181`
- `save_contact(...)` — the sole write path. `013:184-210`
- `reveal_application_contact(...)` — the same for an application, as a separate function: two different routes to a contact should read as two different events. `014:59-113`
- `forget_candidate(...)` — right to erasure: contacts and matches deleted, invitations → `withdrawn`, profile → `deleted` with transcript and extraction nulled out. `014:116-145`

All of them carry `SET search_path = pg_catalog, product`. Without it the function can be tricked by putting a hostile schema ahead of `product` — the classic `SECURITY DEFINER` attack.

That single perimeter has **15 tests**: five SQL variants proving access is impossible, an empty `information_schema.role_table_grants`, closed at `sent`, open after `accepted`, an outsider blocked even after acceptance, `declined` revealing nothing, and the disclosure landing in the audit log.

### Story 2. Tenant isolation: RLS on 27 tables

Context is set via `set_config(..., is_local => true)` — it lives until the end of the transaction and **cannot leak into the next request served by the same pooled connection**. There is a dedicated test for exactly that. — `app/db.py:53-85`

The key principle, worth quoting verbatim: **an unset context means "you see nothing," not "you see everything."** Forget the context and you get an empty result, which is the correct behaviour.

Two policy layers:
- by tenant — `ishmed.clinic_id`
- by role within the tenant — `ishmed.member_role` → `product.is_manager()`, wrapped in `coalesce(..., false)`. **An unknown role narrows privileges, it never widens them.**

Two-sided policies where data belongs to two parties: `matches`, `invitations`, `applications`, `interviews` and `interview_turns` are visible to both clinic and medic, but the `WITH CHECK` on writes admits the clinic side only.

`product.users`, `sessions` and `user_credentials` are **deliberately without RLS**: they are read before any context exists (a medic is looked up by `telegram_user_id`, a session by its token hash). A context-dependent policy would make logging in impossible. That is a documented decision in the migration, not a forgotten table. — `013:42-47`

A separate subtlety worth telling: `product.user_clinic()` breaks a circular dependency at login. `clinic_members` is closed by RLS on `clinic_id`, yet at login time the tenant context is not known — and the only place to learn it is `clinic_members`. The function answers exactly one question and returns nothing else.

### Story 3. Business rules as database constraints, not as code

- **`ck_matches_reasons`**: `NOT hard_constraints_passed OR array_length(reasons,1) >= 2` — a match without two explanations **physically cannot be stored**. Explainability expressed as a constraint rather than as a code review habit.
- **`ck_credentials_hash_is_argon2`**: `password_hash LIKE '$argon2%'`. `accept_employee_invite()` raises `check_violation` on a non-argon2 argument: **the password does not pass through even in transit.**
- **`staff_positions.seats_open`** is a generated column, `GENERATED ALWAYS AS (seats - seats_filled) STORED`. "Vacant / filled" is not a toggle but a derivative of fact: the `tr_employees_recount` trigger recomputes on hire, dismissal and transfer — and on a transfer it recomputes both positions.
- **`ck_users_consent_pair`**: `(consent_at IS NULL) = (consent_version IS NULL)` — half-consent does not exist as a state.
- **`ck_reviews_callback`**: a callback request without a phone number will not save.
- **Rate limiting inside the intake function:** web is 1 review per `(target, ip_hash)` per hour, Telegram is **1 per target per 24 hours**. The thresholds differ deliberately: a Telegram account is a durable identity, and changing an IP is easier than changing an account. Each limit has its own index.
- **`is_correct` is closed by a column-level grant:** `GRANT SELECT (id, question_id, clinic_id, position, text)`. The application role cannot read the correct answer. Options are shuffled by `ORDER BY md5(option_id || attempt_id)` so "the right one is always first" never becomes a strategy. Attempt review unlocks only once `finished_at IS NOT NULL`, otherwise it is a way to peek at answers.
- **Dictionaries are extended by migration, not by the application** (`025`): matching is computed from them, and free-text entry would destroy candidate comparability.

## 6. QR reviews — the full working loop

This is what gets demoed live.

1. A manager clicks QR on a unit or an employee → `ensure_*_review_target()` (idempotent; `clinic_id` is derived **from the node itself**, and another clinic's node raises `insufficient_privilege`).
2. `segno` renders the QR **on the fly, never written to disk**: a file would need invalidating and cleaning up, while drawing takes milliseconds. SVG for print (vector plus the mandatory quiet zone), PNG for screens.
3. The slug is 12 characters from a **confusable-free alphabet**. It is short also because a deep link caps the `start` parameter at 64 characters, and less data in a QR means larger modules and more reliable scanning at distance.
4. The patient points a camera → `t.me/ishmedsifatbot?start=<slug>` → 1–5 rating buttons → optional text, voice or photo. Voice goes to STT.
5. If someone opens the bot without a QR, we **do not offer a list of rooms to pick from.** They do not remember where they were, and we would end up with reviews attached at random.
6. The fallback web form at `/r/{slug}` is server-rendered Jinja2 with inline CSS, about ten kilobytes. React is not shipped there: the patient opens it on mobile data in a hallway, and pushing 280 KB of SPA for one form is not engineering. A honeypot field handles naive bots.
7. Surveys are deactivated rather than deleted: the code is printed and stuck on a wall, and deleting the target would turn that sticker into a dead link with no explanation.
8. The cabinet surfaces the **reason**, not the average: per-tag statistics on what people ask to improve, filters for low ratings, unhandled items and callback requests, plus a "handled" mark with an author.

Health, diagnosis and treatment are **never** asked about — the tag list is closed (6 service aspects) and the intake function rejects any tag outside the dictionary via `<@`. The test for this pushes a SQL injection through the tag field.

Files are never stored on our side, only the Telegram `file_id`. An `ip_hash` replaces the address, salted from the application key so the hash cannot be checked against a ready-made rainbow table.

## 6a. Bilingual: why this is engineering, not a translation file

Uzbekistan is bilingual, and for a nurse from a rural district Russian text is a barrier rather than an inconvenience. All three surfaces run in Russian and Uzbek.

**Language is a property of the person, not of the surface.** It lives in `product.users.locale` (an `ru`/`uz` enum) and is shared between bot and cabinet.

| Surface | Where language comes from | Switch |
|---|---|---|
| `@ishmedbot` | `users.locale`, set at `/start` | `/language` |
| `@ishmedsifatbot` | Telegram `language_code` | a button under the greeting |
| Cabinet | `users.locale` via `/api/auth/me` | a segmented control → `POST /api/auth/locale` |

**Completeness is held mechanically, not by attention.** This is the main point to make: a hole in a translation does not break the app — it silently falls back to Russian, and an Uzbek speaker mid-Uzbek-conversation gets a Russian sentence. The audience notices, not you. Hence:

- on the backend, `tests/test_i18n.py` checks key parity **and placeholder parity** for `{...}`: if the Russian string has `{count}` and the Uzbek one does not, the test fails;
- on the frontend the Uzbek table is declared as `Record<Key, string>` off the Russian one — **a forgotten key does not compile**;
- a missing key renders at runtime as `[key]`, not as emptiness.

**Grammar, not string interpolation.** Russian needs three plural forms and different cases: "6 вопросов", but "опыт от 3 **лет**", not "от 3 года". Hence `plural(n, prefix, locale)` and separate genitive keys. Uzbek nouns do not inflect after a numeral, so all three forms coincide and the rule stays single rather than branching per locale. Both real bugs — "от 3 года" and a detached suffix "3 yil dan" instead of "3 yildan" — were caught by the test, not by eye.

**Deliberately not translated:** the interview plan questions and the clinic-authored vacancy greeting. Rationale in §4.

A patient review stores the language it was actually left in, not the one set in their Telegram client — they may have switched it with the button.

**Honest about quality:** the Uzbek was written without a native speaker. Completeness is guaranteed; phrasing is not. That is a named debt, not an omission.

## 8. Clinic authentication

argon2id, with the hash in a **separate table** so it never lands in a general `SELECT` on the user or in a serialiser. The cookie holds a random token; the database holds only its `sha256`. A test asserts the token appears nowhere in the database in plaintext.

Identical response **and comparable timing** for an unknown email and a wrong password — otherwise the login form becomes an account enumeration oracle. A 15-minute lockout after 8 attempts, with the counter **in the database rather than in process memory** (otherwise a restart resets the defence), and `Retry-After` on the response. Expired sessions are purged at service startup: it restarts on every deploy, so no separate schedule is needed.

Management sections have two barriers: RLS in the database **and** a 403 at the HTTP layer. Not redundancy — RLS already refuses to hand over another tenant's data, but an explicit 403 beats an empty list, because otherwise you cannot tell "broken" from "not allowed."

A found-and-fixed bug worth telling as its own story: employee portal invitations originally granted the `recruiter` role instead of `employee`, so a rank-and-file employee received manager privileges. Migration 022 fixed it along with an `UPDATE` for already-created accounts, and it now carries a regression test plus a check that an employee sees zero rows across seven management tables.

## 9. Likely questions and answers

**"Where is the AI beyond speech recognition?"**
Four live deployments on distinct jobs: `gpt-5` parses vacancy free text into fields and assembles interview summaries, `gpt-5-mini` decides whether a candidate's answer is sufficient, `gpt-4o-transcribe` handles voice, `tts` reads questions aloud. Every call is written to `ai.model_calls` with latency and tokens — which is why the cost of an interview is counted rather than estimated: $0.0053 in text, $0.0076 with voice.

**"So where is the agent? LangGraph is in your dependencies."**
> We wrote it and threw it away — more precisely, we stopped once it was clear the problem was a different shape. The interview is a deterministic state machine: question order is fixed by the plan, and the state already lives in two tables. A checkpointer would have added a second source of truth and a divergence risk for no gain. A graph becomes justified on branching — different question lines depending on answers; the database would stay the store and the checkpointer would own only the position in the graph. The `agent` schema, with write access scoped to exactly itself, is already standing by. This is not "we could not manage it," it is "we did not need it, and we can tell you when we will."

**"Why not vector search for matching?"**
We tried it and rejected it on the data. The source catalogue held 1,305 doctor-side titles against 54 nursing titles — a 24:1 ratio. On that distribution semantic search consistently ranks a doctor above a nurse for a nursing vacancy. In medical hiring that is not "imprecision," it is an unacceptable result: role category is a hard constraint, not a preference. Hence deterministic matching, with `ck_matches_reasons` demanding at least two reasons per match.

**"Why no Docker or Kubernetes?"**
One VM, two cores. Docker there consumes resources without paying for itself. systemd with `Restart=always` and sandboxing covers the same ground. Once there is a second machine, the conversation changes.

**"How do you know the privacy actually holds?"**
`make verify`: ruff, a secrets scan, and 154 tests against a live database under the application role. The "no access to contacts" test is a regression barrier: if it fails, the test is not what broke.

**"You're not scraping anyone?"**
Not any more. Migration 023 dropped the imported catalogue — 3,595 vacancies and 773 organisations from a government portal, along with their embeddings and the hybrid search. The database now holds only vacancies a clinic published itself. It went from 93 MB to 12 MB after the cleanup.

The **how** is worth telling separately, because it shows the level: not `DROP SCHEMA CASCADE`. Eleven `updated_at` triggers in the `product` schema called a function in the schema being dropped, and a cascade would have removed them silently — the field would simply have stopped updating across the whole product. The function was moved and the triggers were re-pointed **by iterating `pg_trigger`** rather than working from a list, so a forgotten trigger would not announce itself later through data quietly going stale.

**"What will break during the demo?"**
Telegram polling is single-consumer: if the server bot is up, the local one refuses to start, and vice versa. Network reachability to Azure is the only external dependency. Unfinished cabinet sections show honest empty states rather than invented cards: at a rehearsal fake data is easy to mistake for real, and that is the worst possible way to discover a section does not work.

## 10. Known debts — know them so you are not ambushed

If the judges find these before you do, it lands worse. Better to name them yourself.

**Permission holes — fix before the demo if there is time:**

1. **`product.course_answer_key()` does not check for manager role.** The comment says "only by the clinic owner"; the body only matches `clinic_id`. An employee with a context set can pull the answer key and bypass the entire column-grant perimeter around `is_correct`. One `is_manager()` line closes it.
2. **`p_candidates_own` was not rewritten for roles.** Migration 022 lists `candidate_profiles` among management tables but never changed the policy, so an `employee` sees every active candidate profile. Tests miss it — the table is absent from `MANAGEMENT_TABLES`.
3. **`attach_to_review()` does not verify rights on the specific review.** Knowing a `review_id` is enough to attach to any of them. The current protection is that `review_id` was just returned by `submit_review_telegram`.

**Unfinished scope:**

4. **The courses schema exists; the API and UI do not.** Six tables, grading, shuffling, the column-level grant — all in migration 021. The "Training" section in the cabinet is a stub.
5. **Matching and invitations are not written.** The `matches` and `invitations` tables and `ck_matches_reasons` exist; the pure ranking function does not. The "Candidates" section is a stub.
6. **The candidate profile is not enriched from the interview.** `extraction` is produced and stored in `interviews`, but `candidate_profiles` stays a draft.
7. **The candidate's name is not shown in the cabinet** — only "Candidate <8 chars of id>". That is deliberate (the contact is closed until the application is accepted), but it is awkward for managers and there is no decision yet.
8. **No reminder for abandoned interviews.** Nobody sweeps `status='in_progress'` rows with a stale `last_activity_at`.

**Process and infrastructure:**

9. **`test_rls_is_enabled_on_all_tenant_tables` checks 10 tables out of 27.** Its docstring calls it "insurance against a new table nobody closed with a policy" — the insurance has fallen behind the schema.
10. **Dead grants** on the dropped `core.*` and `ai.search_vacancies` remain in 011. Migrations are immutable, so cleanup means a new file.
11. **No CI.** `make verify` is run by hand, because the tests need a live database over an SSH tunnel.
12. **The Uzbek was written without a native speaker** — both in the bots (`app/i18n/uz.py`) and in the cabinet (`frontend/src/lib/i18n.tsx`). Key completeness is held by tests and types, but the quality of the phrasing is unverified, the consent text least of all. This is the only localisation debt left: the bilingual machinery itself works across all three surfaces.
13. **The prompts are not fully obeyed.** The model adds requirements that were not in the text and glues two questions together with "and", though the prompt forbids it. That is why both steps pass through a manager's edit instead of being saved silently.
14. **A bot token leaked into a chat** — it needs `/revoke` via @BotFather before any public demo.
15. Nightly dumps sit on the same disk as the database. Azure Backup for the VM is not enabled.
